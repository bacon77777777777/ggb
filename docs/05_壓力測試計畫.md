# 吉吉比（GGB）壓力測試計畫

> 一次性活動，不是回歸清單。回歸測試在 `02_前後台測試案例.md`。
> 最後更新：2026-08-05

---

## 一、為什麼要做

上線前確認三件事：

1. **熱門商品擠得住嗎** —— 剛上架的一番賞是所有人同時擠的地方
2. **500 筆商品的後台還能用嗎** —— 列表、報表、對帳的查詢會不會爆
3. **AI 排程與抽獎搶資源嗎** —— 25 個 cron job 與真實流量並存

不是為了「跑出一個很大的 QPS 數字」。

---

## 二、環境

**主戰場：PROD。** STG 的資料量與排程都跟正式差太多，測出來的數字沒有參考價值
（STG 目前 0 個 cron job、3 千筆抽獎紀錄；PROD 25 個 job、1.1 萬筆）。

### 已知的環境天花板

| 項目 | 數值 | 影響 |
|---|---|---|
| Supabase pooler（session mode） | **15 connections** | 超過就 `EMAXCONNSESSION`，這是實測撞到的第一道牆 |
| 同商品抽獎（實測，STG） | 12 併發 252 ms、單筆中位數 212 ms | 含 psql 連線成本，走 API 會更快 |

**壓測腳本必須走 HTTP API，不能用 psql 併發** —— 否則量到的是連線池上限，不是系統能力。

## 四、要測什麼

### 4.1 同商品併發（最重要）

**這是最可能出事、也是唯一改過設計的地方。**

原本 `pg_try_advisory_xact_lock` 拿不到鎖就回 `PRODUCT_BUSY`，商品越熱門失敗率越高。
migration 453 已改為 `pg_advisory_xact_lock`（等待）+ `lock_timeout 5s`，
正確性由 migration 451 的唯一索引 `uq_draw_records_ticket` 保證。

已在 STG 驗過：

- 12 個不同使用者抽**不同籤** → 12/12 成功、0 重複、整批 252 ms
- 12 個不同使用者搶**同一張籤** → 1 人成功，11 人收到 `TICKET_ALREADY_DRAWN`，該籤被領走剛好 1 次

壓測要量的是：

| 指標 | 為什麼 |
|---|---|
| 單商品在 50 / 100 / 200 併發下的 P50 / P95 延遲 | 決定熱門檔期的實際體驗 |
| `lock timeout` 觸發率 | 超過 5 秒代表已經塞爆，這個比例就是「賣不動」的比例 |
| 同商品每秒成交數 | 交易時間的倒數，是硬上限 |

**若 P95 超過 3 秒**，代表單商品序列化撐不住，要往「拆成多個獨立籤池」或
「把扣庫存移出交易」的方向改 —— 那是設計變更，不是調參數。

### 4.2 排籤封存的尖峰

500 筆商品上架 = 500 次排籤。一番賞 1000 張籤要：
展開 1000 筆、洗牌、組 1000 行文字、算 SHA-256、寫 1000 元素陣列。

要量：**單筆封存耗時**（依籤數）、批次上架 500 筆的總時間。
這是原本計畫裡不存在的負載（封存機制是 8/4 才上線的）。

### 4.3 抽籤販售

3~5 檔，但它多一種鎖競爭型態（`play_lottery` 同樣吃兩把鎖），而且是最沒被真實流量驗過的功能。

要量：每人次數上限在併發下擋不擋得住（同一人同時送 10 個請求）。

### 4.4 後台查詢

500 筆商品下的：商品列表分頁、財務對帳、代幣帳、殺率頁（會撈全部商品與品項）、
封存對照表（1000 張籤的逐籤對照）。

### 4.5 金流

ECPay callback 併發 + 冪等性（`webhook_events`）。

## 五、執行順序

1. 記錄 cron 原狀 → 關閉非必要排程
2. 執行 427 清資料（**在 transaction 內，確認輸出無誤再 COMMIT**）
3. 建立 500 筆商品 + 4~6 個機台主題
4. 基準測試：單商品單人抽獎的延遲（沒有競爭時的底線）
5. 逐級加壓：同商品 10 → 50 → 100 → 200 併發
6. 全站混合流量
7. 後台查詢
8. 恢復 cron

## 六、已定案的做法

- **假用戶**：用 Supabase Admin API 建（`POST /auth/v1/admin/users`），不能直接寫
  `auth.users` —— 那樣建出來的帳號 GoTrue 認不得（缺 `identities`），登入直接 500。
  建完再補 `public.users`（`is_bot = true`，避免污染報表）。
  清除要連 `auth.users` 一起，走 Admin API 的 DELETE。
- **流量產生器**：`backend/scripts/loadtest.mjs`，零相依（只用 Node 內建 fetch）。
  走 Supabase PostgREST + 真實使用者 JWT。
  **不能用 psql 併發** —— session mode pooler 上限 15 connection，量到的是工具天花板。
  登入要分批（一次 60 個同時送會被 GoTrue 限流，只成功一半）。
- **時段**：STG 隨時可跑。PROD 需要先清資料，那是不可逆操作，要老闆當次明確授權。

## 七、2026-08-05 STG 實測結果

見 `DEVLOG.md` v2026.08.05c。摘要：

- 單一熱門商品吞吐 **~60 成功/秒**，併發 25→200 不變（序列化上限）
- 全站混合流量 **210 成功/秒**，p95 868 ms
- **零 `PRODUCT_BUSY`、零 `LOCK_TIMEOUT`**
- 封存排籤 6 ms/檔，不是瓶頸
- 後台查詢扣掉連線成本後都在個位數毫秒
